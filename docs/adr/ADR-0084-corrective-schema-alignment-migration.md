# ADR-0084: Align migration chain with schema.prisma via forward-only corrective migration

- Status: accepted (2026-10-04/05)
- Context: `prisma migrate status` on any freshly migrated DB vs `prisma/schema.prisma` showed 147 lines of drift: `20260525_home_intelligence/migration.sql` is a declared-empty stub (`SELECT 1`), `20260525_monetization` covers only part of the monetization models, and `20260525180000_social_layer.sql` (48 KB) sat inside `prisma/migrations/` but was never a Prisma migration (ignored by the engine). Result: models such as `CommentLike`, `BusinessHours`, `home_content_configs`, `service_rates_by_location`, `demand_analytics`, `service_form_templates`, `group_service_sessions(+attendees)`, enum variants `OrderPhase.draft` / `PaymentStatus.releaseScheduled`, and several Company/User/Post columns existed only in `schema.prisma`. The dev DB (no `_prisma_migrations`) had been `db push`-synced to schema state, so the gap was invisible locally but blocked fresh installs and upgrade rehearsals.
- Decision: add ONE forward-only corrective migration `20261004120000_align_schema_with_models` generated with `prisma migrate diff --from-url <fresh-67-migrated> --to-schema-datamodel prisma/schema.prisma --script`, then hand-reviewed and made idempotent (guarded `CREATE TYPE`/`ADD VALUE`/`ADD COLUMN`/`CREATE INDEX`/`CREATE TABLE`/constraint drop+add). Move the stray `social_layer.sql` to `prisma/legacy/` (README added) so the migrations directory contains only engine-recognized migrations. Environments that were db-push-synced (dev) are NOT migrated in place — the documented path is `migrate resolve --applied` baselining, gated on owner approval.
- Alternatives considered: (a) `prisma migrate dev` re-baselining the whole chain — rejected, rewrites history; (b) `db push` as the release mechanism — rejected, non-reproducible and forbidden for release; (c) splitting corrective DDL back into edited historical migrations — rejected, forbidden (would break checksums for any DB that applied them).
- Consequences: fresh installs and legacy-history DBs both converge to exactly `schema.prisma` (verified: diff "No difference detected" on two fresh DBs and on the upgraded legacy DB with representative data preserved). Documented one-way steps inside the corrective migration: drop `PostReaction` (model removed from schema; 0 rows on dev), drop `PostComment.userId` (replaced by `authorId`), recreate `PostMedia.type`/`Post.moderationStatus` as enums, `Service.price` double→integer (49.5→50 rounding observed in rehearsal).
- Rollback strategy: the migration is forward-only; rollback = restore from backup / re-deploy prior release. Because it only aligns structure with the already-shipped `schema.prisma`, application behavior is unaffected; the previous release remains deployable against the migrated schema.
